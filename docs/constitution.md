# KQ Quant Tool — 프로젝트 헌법

이 문서는 본 프로젝트가 **반드시 지켜야 할 절대 규칙**을 정의한다.
모든 PRD, Task, 구현은 이 헌법에 위배되어선 안 된다.

---

## 1. 프로젝트 정체성

### 1.1 목적
- 한국 주식 시장 (KOSPI + KOSDAQ) 퀀트 분석 도구
- AI Quant 3기 프로젝트 발표용
- 학술적 검증 가능한 방법론 사용

### 1.2 강점 (Strength)
- 12년 FnGuide 데이터 (재무 + 가격)
- Alpha Decay 핵심 차별점
- 위험기반 자산배분 (GMV/MDP/ERC)
- 계층적 매크로 국면 모델 (TabPFN + HMM)

### 1.3 사용자
- 본인 (개발자 + 발표자)
- 팀원 3명 (검증 + 데이터 보조)
- 발표 평가자 (교수 + 동료)

## 2. 데이터 규칙

### 2.1 데이터 누수 방지 (Look-ahead bias)
- ✋ 시그널 계산 시 **t 시점 이후 데이터 절대 사용 금지**
- ✋ 백테스트에서 동일 봉의 신호 + 체결 동시 처리 금지
- ✋ 시그널 발생 = T일 종가, 체결 = T+1일 시가 (기본 가정)
- ✋ 미래 정보로 학습된 모델을 과거 데이터에 적용 금지

### 2.2 생존편향
- 상장폐지 종목을 임의로 제외하지 않는다
- 만약 제외한다면 **명시적으로 PRD에 기록**

### 2.3 가격 데이터
- **차트 표시**: 실제 종가 (수정 미반영)
- **백테스트 계산**: 수정 종가 (분할/배당 반영)
- **현재가**: yfinance 실시간 우선, 실패 시 엑셀 최종 종가
- 두 데이터를 섞어서 표시하지 않는다

### 2.4 결측치
- 재무 데이터 결측 → 명시적 처리 규칙 (forward-fill / 제외 등)
- 백테스트 결과에 영향 시 PRD에 명시
- 결측 종목을 임의로 제외하지 않는다

### 2.5 외부 데이터
- yfinance 의존도 낮춤 — 엑셀 데이터 우선
- API 키 필요 시 환경변수 사용 (코드에 직접 작성 금지)
- KRX, ECOS 등 외부 데이터 추가 시 PRD 필수

## 3. 모델 / 알고리즘 규칙

### 3.1 학술적 변호 가능성
- 모든 사용 알고리즘은 **표준 학술 출처** 인용 가능해야 함
- 발표 시 "왜 이걸 썼나?" 질문에 한 줄로 답할 수 있어야 함
- 신박함 ≠ 검증 안 됨. 검증된 신박함만 사용

### 3.2 표본 크기 vs 모델 복잡도
- 분기 데이터: 49개 → 단순 모델만 (LightGBM, TabPFN, HMM)
- 일별 데이터: 3,000+개 → 대부분 모델 가능
- 표본 < 100 → 딥러닝 금지

### 3.3 과적합 방지
- 학습/검증 분리 명시
- Cross-validation 결과 기록
- 백테스트 성과가 비현실적이면 데이터 누수 의심

### 3.4 모델 폴백 (Graceful Degradation)
- 외부 의존성 (TabPFN 라이선스 등) 실패 시 자동 폴백
- 폴백 모델: LightGBM → 규칙 기반
- 폴백 시 사용자에게 명시적 알림 ("Powered by ..." 배지)

## 4. 코드 규칙

### 4.1 단일 파일 정책
이 프로젝트는 의도적으로 **단일 파일 위주** 구조다:
- `server.py` — 모든 API + 분석 로직
- `index.html` — 모든 UI + JS
- `data_loader.py` — 모든 데이터 처리
- `regime_model.py` — 모든 매크로 국면 모델

장점: 발표 / 평가 시 코드 추적 쉬움
단점: 파일이 커짐 → 변경 위치 명확히 명시 필요

### 4.2 인터페이스 안정성
- 기존 함수 시그니처 변경 금지 (호출하는 곳 영향)
- API 엔드포인트 제거 금지 (기존 클라이언트 호환)
- 새 기능 추가 = 새 엔드포인트 + 새 함수

### 4.3 명명 규칙
- 함수: `snake_case` (Python)
- 변수: `snake_case`
- 클래스: `PascalCase`
- HTML id: `kebab-case` (예: `s-price`, `regime-prob-bars`)
- JS 함수: `camelCase` (예: `loadMacro`, `renderRegimeAI`)

### 4.4 문서화
- 모든 함수에 docstring (한국어 OK)
- 복잡한 로직에 인라인 주석
- API 응답 JSON 스키마 PRD에 명시

## 5. 워크플로 규칙

### 5.1 변경 절차
모든 새 기능은 다음 순서로 진행:
```
PRD → Task List → 한 작업씩 구현 → 사용자 검증 → 다음 작업
```

### 5.2 한 번에 하나
- 한 번에 하나의 작업만 수정
- 여러 파일 동시 수정은 단일 작업 안에서만
- 동일 파일 3번 이상 수정 시 → 작업 재분해 필요

### 5.3 롤백 정책
- 작업 실패 시 그 작업만 롤백
- 다른 작업 결과 보존
- 절대 전체 reset 금지

### 5.4 테스트 강제
- 백엔드 변경 → `curl` 또는 단위 테스트
- 프론트엔드 변경 → 브라우저 시각 검증 (캡처)
- 두 가지 모두 통과해야 [x] 처리

## 8. 절대 금지 사항

다음은 어떤 이유로도 금지:

- 🚫 데이터 누수 (look-ahead bias)
- 🚫 백테스트 결과 조작 (수익률 부풀리기)
- 🚫 미래 데이터로 학습한 모델을 과거에 적용
- 🚫 코드에 API 키 / 비밀번호 작성
- 🚫 다른 사람의 코드 / 모델 출처 미표시
- 🚫 검증 없이 작업 완료 처리
- 🚫 사용자 승인 없이 큰 구조 변경

## 9. 가치 우선순위

충돌 시 다음 순서로 결정:

1. **정확성** (데이터 / 계산 정확)
2. **재현성** (다른 PC에서도 동작)
3. **학술적 변호 가능성** (발표 대비)
4. **안정성** (시연 시 에러 없음)
5. **사용성** (UI 직관)
6. **속도** (응답 빠름)
7. **코드 미학** (코드 정돈)
